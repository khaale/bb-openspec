# OpenSpec в bb: исследование и предложение

Дата: 2026-10-28. Исследованы каталог установленного bb, комплектный Tasks (manifest, skill и каталог возможностей), документация Plugin SDK и исходники трёх публичных плагинов. Плагины не устанавливались и не запускались; описание UX основано на коде и документации, а не на проверке в живом приложении.

## Существующие решения

| Плагин | Наблюдаемая модель | Что применимо |
| --- | --- | --- |
| Tasks (поставляется с bb, устанавливается отдельно) | Список и доска; проекты, подзадачи, комментарии; делегирование по preset; связанные worker threads; CLI и карточки в сообщениях | Связь задачи и треда, показ прогресса, контекст агента |
| Apple Style Tasks | Разделы, вложенные шаги, детали задачи, помощь с идеей/декомпозицией/шагом; результаты помощи принимает пользователь; SQLite | Простой чеклист и компактные детали |
| Linear | Список с группами, поиск, карточка issue, header chip и панель треда; текущая/активные/прошлые задачи треда; локальное зеркало | Список в узкой панели, явная привязка треда, разделение просмотра и принятия в работу |
| Command Center | Доска Queue / In progress / In review / Done, отдельный Needs you, переход к треду; ручное завершение; интеграция с Tasks | Отдельно показывать ожидание решения человека; не считать завершение хода агента завершением задачи |

Источники:
- Tasks: `bb plugin search task --json`; комплектные `server/dist/builtin-plugins/tasks/package.json` и `skills/tasks/SKILL.md` в установленном bb.
- [Apple Style Tasks](https://github.com/dmitriikapustin/bb-plugins-by-kapustin/tree/HEAD/plugins/my-tasks): `app.tsx`, `server.ts`.
- [Linear](https://github.com/vburojevic/bb-plugin-linear): `README.md`, `app.tsx`.
- [Command Center](https://github.com/dilipgv/bb-plugin-command-center): `README.md`, `app.tsx`, `server.ts`.
- [Plugin Guide](https://getbb.app/plugin-guide) и локальный навык bb-plugin-authoring: frontend-registration, quickstart, testing.

## Рекомендуемая модель

Карточка верхнего уровня — change. Пункты tasks.md — чеклист внутри. Так изменение видно ещё до появления задач, а proposal/specs/design сохраняют связь с реализацией. Отдельный общий список пунктов можно добавить позже.

Содержимое и прогресс читаются из OpenSpec. В базе bb достаточно хранить связи с тредами и настройки отображения. Создание дубликатов в Tasks добавит двустороннюю синхронизацию, поэтому для первой версии предлагается самостоятельный плагин.

Не следует приравнивать наличие артефактов к согласованию, все галочки — к успешной проверке, а завершение хода агента — к завершению изменения. Макет разделяет артефакты, выполнение задач и активность треда. Описательные группы доски, если появятся, вычисляются из фактов; перетаскивание не должно произвольно менять workflow OpenSpec.

## Техническая осуществимость

SDK документирует navPanel, вкладки/панели треда, header action, RPC, realtime, файловый SDK и host entry. Этого достаточно для предлагаемого интерфейса без изменения ядра bb. Конкретные сигнатуры, поддержка наблюдения файлов на выбранной машине и проверки конкурентной записи требуют проверки на этапе реализации.

Путь OpenSpec необходимо разрешать в выбранном checkout/environment, а не только по projectId: worktree могут содержать разные изменения и прогресс. Смена окружения должна менять источник явно. В первой версии плагин не редактирует tasks.md: статусы обновляет агент, интерфейс перечитывает файл.

Статусы артефактов желательно получать через JSON CLI OpenSpec с учётом schema, а чеклист — читать из файла. Нельзя навсегда зашивать четыре артефакта для пользовательских схем. В MVP допустимо явно ограничить поддержку стандартной spec-driven; это ещё надо согласовать.

## Предложение для первой версии

1. Выбор проекта и окружения, активные/архивные изменения, поиск.
2. Карточка change с артефактами, чеклистом по группам, прогрессом.
3. Чеклист только для чтения; статусы меняет агент в tasks.md.
4. Обновление после внешних изменений, ошибки чтения и пустое состояние.
5. Явная привязка существующего треда и переход к нему.
6. Запуск нового треда на change с действием «Проработать», «Реализовать» или «Проверить», выбором провайдера и редактируемым первым сообщением; в том же окружении, из которого открыт change.

Кандидаты на следующий этап: продолжение существующего агента из панели, создание change, validate/archive через UI, доска, общий список пунктов.

## Вопросы для согласования

- Основная единица интерфейса: change с вложенными задачами или плоский список всех пунктов?
- Начинаем с просмотра и галочек либо сразу нужен запуск агентов?
- Достаточно spec-driven в первой версии или уже нужны пользовательские схемы?

Макет содержит демонстрационные данные. Переключатели и галочки работают только внутри страницы и не изменяют OpenSpec.

## Концепция 02

После обсуждения пользователь поддержал change с вложенным чеклистом и попросил включить запуск агента, если он не требует чрезмерного усложнения. Новый макет: `docs/mockups/openspec-browser-v2.html`. Добавлены цветовые индикаторы артефактов, кольцо прогресса, вкладка тредов и форма запуска с редактируемым промптом. Все данные и создаваемые треды демонстрационные. Макет не фиксирует окончательный состав MVP; интерфейс ожидает согласования.

## Уточнение интерфейса и статусов

По решению пользователя служебные пояснения об источнике данных и трактовке галочек убраны с основного экрана. Описание change содержит краткое назначение изменения. Чеклист только для чтения; агент управляет статусами и артефактами, плагин отображает их и обновляется при внешних изменениях. Ручное изменение статусов через UI не входит в первую версию.
